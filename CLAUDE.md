# Job application agent

Local daily pipeline: discover recent ML/Data roles from employer ATS job feeds (Greenhouse, Lever, Ashby, Workday, Amazon, Google Careers), score and dedupe them in a SQLite ledger, tailor the résumé for strong fits and Google, and fill and submit applications in the agent's Chrome. Workers submit only while `config.json` has `submit_applications: true` (the ledger refuses `submit` otherwise); with it `false` they stop at the final Review page.

## Commands

- All tests: `python3 -m unittest` (stdlib only; no dependencies, build step, or linter).
- One test: `python3 -m unittest tests.test_core.CoreTests.test_hard_filters`.
- Ledger CLI: `python3 -m job_agent --help`. Every subcommand prints JSON; errors print `{"error", "type"}` and exit 1. `--config` / `--db` override the defaults (`config.json`, `data/job-agent.sqlite3`) — point them at temp paths when experimenting so the real ledger is untouched.
- Feed discovery: `python3 -m job_agent fetch-feeds --registry data/company-registry.json --out artifacts/YYYY-MM-DD/discovered.json` pulls the Greenhouse, Lever, Ashby, Workday, Amazon and Google Careers boards listed in the registry concurrently (stdlib `urllib` only), keeps recent ML/Data postings in the preferred locations, and writes the `discovered.json` array that `discover` ingests (`source: "ats-api"`). It prints per-board stats (`fetched`, `kept`, `skipped`, `errors`); a failing board is reported, not fatal. `--queries` only matter for Amazon's search API; `--max-pages` bounds the newest-first walk per Workday board and Amazon query. Google Careers has no API: its results pages embed each job as JSON (`ds:1`), searched newest-first per query (default the old Google bot's queries and Bay Area offices; a registry entry's `queries`/`locations` override) with Senior/Staff/PhD/early-career titles dropped. `--recency-hours N` makes a backfill run: scoring uses N for that run and the next run's window ignores it. Workday and Amazon only give day-level dates, so those rows get `posted_at` at the end of that day (config `timezone`) and `posted_at_precision: "day"`. The registry is `data/company-registry.json` (gitignored with the rest of `data/`; copy `company-registry.example.json` from the repo root, one entry per company with `ats` and the board `token`, or `host`/`tenant`/`site` for Workday; Google is just `{"company": "Google", "ats": "google"}`). Parsers live in `job_agent/feeds.py`; `tests/test_feeds.py` covers each ATS with canned fixtures in `tests/fixtures/feeds/`.
- Scheduled runs: `scripts/install-schedules.sh` (re-run after editing schedules; `--uninstall` removes them). Run one by hand with `scripts/run-automation.sh job-pipeline`.

## Architecture

The work is split between a deterministic Python ledger and LLM instructions:

- `job_agent/core.py` holds all state and rules: URL canonicalization (tracking params stripped, identity params kept), dedupe by canonical URL and by `(company, ats_job_id)`, the ATS behind each job (`ats` column, from the application URL's host or the feed), rule-based scoring with hard filters (internship, management, citizenship/clearance, >5 years, recency, non-ML role, location — `location_matches`, shared with discovery: a remote flag counts only with a US place or a bare "Remote", so Europe-only Ashby "remote" roles are dropped) whose 0–25 skills points are job-fit-scorer's `skill_score` (a `skill_keywords` count only when a job has none), company-policy matching, atomic claims (never two claimed jobs from one company, so parallel workers never share an account), and the idempotent email digest. `cli.py` is a thin argparse wrapper.
- Job status flow: `discovered` → `scored` | `skipped` | `manual_review` → `queued` (every job with fit ≥ `minimum_fit_score`, or ≥ `limited_company_minimum_fit_score` (default 90) at a company with an application limit; no daily cap) → `claimed` → `submitted` | `ready_for_review` | `blocked`; a submitted job becomes `withdrawn` when a swap gives its slot away. Each claim is a row in `attempts` (with the claiming run's id); `report` gives the submission rate as submitted attempts / finished attempts (a retry counts again; stale claims count as `abandoned`), blockers by category, and per-run discovery stats. `fetch-feeds` starts the run and stores per-company board stats in `run_boards` (companies checked, postings scanned, kept); the digest lists them. `recover-stale-claims` returns old claims to `queued`; `requeue --job-id ...` does the same for blocked or ready jobs. Application limits: a policy's `application_limit` (Amazon's ten active applications, ElevenLabs' one per 90 days, the latter enforced from ledger submissions) or a worker's `block --category application_limit [--until]` (stored in `company_limits`) makes `claim` skip the company and leave its jobs `queued` (deferred) until the limit expires or `clear-limit --company X`; `limits` lists them. A policy's `swap` (Amazon: `max_active` 10, fit gain ≥ 10, ≤ 2 withdrawals a run) lets the orchestrator free slots itself: `swap-plan --active-file` (the site's active list) pairs the weakest withdrawable application with the strongest queued job, and `withdraw` records the on-site withdrawal and lifts the cap; `report` and the digest list withdrawals. `report` also breaks attempts down `by_ats` and `by_company`. Tailored résumés: every queued job with fit above `tailored_resume_above_fit_score` (config, default 90) or at a `tailor_resume` policy company (Google) is listed by `tailor-queue`; the `resume-tailor` agent rewrites the base résumé (exported from the "Resume Working Draft" doc named by `resume_doc` in config) with the same facts and runs `render-resume`, which prints a one-page PDF and a résumé-vs-posting screenshot (`job_agent/resume_render.py`, headless Chrome + Quick Look) and records both on the job (`resume_path`, `resume_compare_path`); `claim` returns the job's `resume_path` (tailored PDF, else the approved résumé). `record-applied` records an application sent by hand (Google's dashboard) so windowed limits count it. `complete` and `submit` require `--resume-verified`; `submit` also needs `--evidence` (the on-page confirmation). Policy companies are re-checked at claim time, so a `manual_review` company is never claimed even if queued earlier.
- `.claude/skills/job-application-pipeline` drives a run: `fetch-feeds` discovery → `resume-text` → `job-fit-scorer` enriches candidates and sets each one's `skill_score` → `discover`/`score` → `resume-tailor` agents for `tailor-queue` → Google dashboard check → up to `max_parallel_workers` (config, default 2) slots each looping `claim` → one `application-worker`, running at the same time in their own tabs → `submit`/`complete`/`block` → blocker retro + to-dos → Gmail recruiter-reply check → `digest` → Gmail send → `finish-run`.
- Schema changes go in `SCHEMA` plus the `ALTER TABLE` migration in `connect_db`, since existing ledgers are reused.

## Layout

- `job_agent/` — ledger CLI: discover, score, company-policies, tailor-queue, save-export, render-resume, record-applied, claim, submit, complete, block, requeue, limits, clear-limit, swap-plan, withdraw, report, digest, recover-stale-claims, finish-run. Ledger at `data/job-agent.sqlite3`; run artifacts in `artifacts/YYYY-MM-DD/` (both gitignored).
- `.claude/skills/job-application-pipeline` — orchestrator for a full run.
- `.claude/skills/application-completion` — one-application worker procedure (authoritative for form behavior, auth, résumé, output). Per-ATS playbooks observed in runs live in its `references/` (workday, greenhouse, ashby, lever, icims, smartrecruiters, successfactors, amazon, google); the skill wins where they disagree. `COMPLETION_CHECKLIST.md` defines "complete" (final Submit visible, every step traversed, résumé attached, no validation errors); the skill's submit-and-confirm section defines "submitted".
- `.claude/skills/company-application-policies` — per-company routing; registry in `references/policies.json` (Google is `auto_apply` with three submissions per 30 days and `tailor_resume`; Amazon and ElevenLabs carry an `application_limit`; `manual_review` routes a company to the user).
- `.claude/agents/` — `application-worker` (Opus, one job, Chrome), `resume-tailor` (Opus, one job's tailored résumé and screenshot) and `job-fit-scorer` (Opus, high effort, read-only; scores skill fit 0–25 by reading each post against `data/resume.txt`, which `python3 -m job_agent resume-text` extracts from the approved résumé).
- `application-profile.md` — source of truth for personal answers. `config.json` — private local config (gitignored; template in `config.example.json`). `approved_resume_path` must be an absolute path the worker session can read: keep the résumé at `data/Jiayi_Yao_resume.docx` (`data/` is gitignored) or start the session with `--add-dir` for its folder, since `file_upload` refuses other paths.
- `local-resume-companion-extension/` — Chrome extension + native host, now the **fallback** attach path (queue with `node local-resume-companion-extension/enqueue-attach.js URL`). The default is Claude in Chrome's `file_upload`, per section 5 of the completion skill; trial and timing in `RESUME_FILE_UPLOAD_TRIAL.md`. Each enqueue adds its own entry under `attach-queue/` (gitignored) and the native host claims entries by atomic rename, so parallel workers can share it; rebuild the host with `native-host/install.command` after changing `resume_native_host.c`. Debugging guide: `RESUME_EXTENSION_DEVELOPMENT.md`.
- Repo lives at `~/code/job-application-agent` (`~/Desktop/job-application-agent` is a symlink kept so Chrome's unpacked-extension path and ID stay valid; macOS blocks launchd jobs from Desktop/Documents).
- Daily job pipeline: Claude desktop scheduled task `job-application-pipeline-daily` (07:00 every day; stored in `~/.claude/scheduled-tasks/`), since it needs Chrome, Gmail and the to-do artifact. It runs only while the desktop app is open (a missed run fires on next launch). It runs from `~/code/job-application-agent-main`, a detached worktree that `scripts/sync-main-checkout.sh` resets to `origin/main` at the start of each run, so feature branches checked out here never reach the daily run; only what is pushed to `main` does. Don't edit or commit there (the sync refuses to overwrite tracked edits). Its `config.json`, `data/`, `artifacts/` and résumé queue file are links back to this checkout. The Chrome extension's code still loads from this checkout.
- `automations/` + `scripts/run-automation.sh` + `scripts/install-schedules.sh` — launchd-scheduled headless runs (Google L4 monitor 09:00/17:00; weekly AI stock report Sat 09:00; `run-automation.sh job-pipeline` still runs the pipeline headlessly by hand). `run-automation.sh` sets each run's model, timeout watchdog, and `--allowedTools` allowlist — a new CLI command or tool a scheduled run needs must be added there. It unsets `ANTHROPIC_API_KEY` so the claude.ai Gmail connector works. Logs in `~/Library/Logs/claude-automations/`; non-repo state in `~/.claude-automations/`.
- `.agents/` and `.codex/` — legacy Codex configuration, kept for reference only; do not edit or rely on them.

## Rules

- Only application workers click a final Submit control, only with `submit: true` from `claim`, at most once per application. Never type passwords. Accounts are created only through agent-vault's `register` tool, which generates the password and saves it to Bitwarden; see the completion skill's auth section.
- Attach only the résumé `claim` names (the approved résumé, or a PDF tailored from it with the same facts), with `file_upload` first and Local Resume Companion as the fallback; never a Cover Letter or optional autofill input. See the completion skill's section 5.
- Email only `notification_email` from `config.json`, and never include contact, demographic, authorization or résumé content.
- `tests/test_agent_instructions.py` pins key phrases in the skills and agents; update it alongside instruction changes.
